# Feature Specification: cc-connect Peer System Notice Isolation

**Feature Branch**: `014-cc-connect-peer-system-notice-isolation`  
**Created**: 2026-05-12  
**Status**: Draft  
**Input**: Multica PC-76: isolate cc-connect-generated queue, rate-limit, and previous-processing notices from allowlisted peer bot runtimes while preserving real peer final output and human/operator feedback.

## Clarifications

### Session 2026-05-12

- Q: What is the transport failure being fixed? -> A: Discord `allow_from_bots` made peer final output visible, but it also made cc-connect guardrail replies from the peer bot account visible as ordinary peer input. That fed queue/rate-limit/previous-processing notices into the other peer runtime and caused feedback loops.
- Q: What provenance is needed? -> A: `core.Message` needs an explicit peer-bot author marker from the platform adapter so core can treat allowlisted peer bots differently from humans/operators without guessing from names or content.
- Q: What should happen to real peer output? -> A: Normal allowlisted peer bot messages in the bound parent channel must still dispatch to the agent runtime as conversational input.
- Q: What should happen to bridge/system notices? -> A: Discord replies authored by allowlisted peer bots are treated as bridge notices and ignored before dispatch. Core also suppresses queue/rate-limit/previous-processing notices when the triggering inbound message came from a peer bot.
- Q: What remains visible to humans? -> A: Human/operator rate-limit and busy feedback stays visible in the channel. The isolation only prevents those notices from being re-ingested by peer runtimes.

## User Scenarios & Testing

### User Story 1 - Peer final output remains visible (Priority: P1)

As a peer bot in the shared Discord parent channel, when the other allowlisted peer posts a normal final answer, my runtime receives it as conversational input.

**Why this priority**: PC-7 depends on peer-bot visibility. The fix must not undo the parent-channel smoke pass.

**Independent Test**: Dispatch an allowlisted Discord bot message with no bridge-notice markers and verify the platform emits one `core.Message` with peer-bot provenance.

**Acceptance Scenarios**:

1. **Given** an allowlisted Discord bot posts a normal parent-channel message, **When** Discord dispatch runs, **Then** the message reaches the core handler.
2. **Given** the message reaches core, **When** core inspects provenance, **Then** it can distinguish the author as an allowlisted peer bot rather than a human/operator.

### User Story 2 - Bridge notices are not delivered to peer runtimes (Priority: P1)

As a peer bot runtime, I should not receive cc-connect queue, rate-limit, or previous-processing notices from another peer bot as conversational input.

**Why this priority**: These notices created the PC-7 feedback loop and kept the pilot substrate blocked.

**Independent Test**: Dispatch a Discord reply authored by an allowlisted peer bot and verify it is ignored before core handler delivery.

**Acceptance Scenarios**:

1. **Given** an allowlisted peer bot posts a Discord reply generated by cc-connect guardrail handling, **When** the receiving Discord adapter processes it, **Then** it does not dispatch a `core.Message`.
2. **Given** an allowlisted peer bot message hits core while the target session is busy, rate-limited, or queue-overflowed, **When** core handles the guardrail path, **Then** no bridge guardrail reply is emitted back into the channel.

### User Story 3 - Human/operator feedback is preserved (Priority: P1)

As the operator, when I send too many messages or hit a busy session path, I still receive the normal visible feedback from cc-connect.

**Why this priority**: Silence is only acceptable for peer-bot guardrails. Humans still need visible transport feedback to recover or wait.

**Independent Test**: Trigger the same rate-limit and busy paths with a non-peer `core.Message` and verify the existing localized replies still send.

**Acceptance Scenarios**:

1. **Given** a human/operator message is rate-limited, **When** core handles it, **Then** cc-connect sends the existing rate-limit reply.
2. **Given** a human/operator message arrives while the session is busy or queue overflowed, **When** core handles it, **Then** cc-connect sends the existing queue or previous-processing reply.

### Edge Cases

- A peer bot message arrives while the receiving agent is already busy: it may be queued silently when capacity exists, but it must not emit a queue acknowledgement into the channel.
- A peer bot message arrives after the queue is full: it must be silently dropped rather than emitting `previous_processing`.
- A queued peer bot message is later dropped because the agent session resets or dies: drop notification must be suppressed for that peer sender.
- A human/operator message on the same paths must continue to receive visible feedback.
- Broad content-prefix filtering is not the primary mechanism; the fix relies on author provenance plus Discord reply metadata for bridge notices.

## Requirements

### Functional Requirements

- **FR-001**: `core.Message` MUST carry explicit author provenance that identifies messages from allowlisted peer bots.
- **FR-002**: The Discord adapter MUST set peer-bot provenance only for bot authors explicitly listed in `allow_from_bots`.
- **FR-003**: The Discord adapter MUST continue dispatching normal allowlisted peer bot final output without requiring a bot mention.
- **FR-004**: The Discord adapter MUST ignore Discord reply messages authored by allowlisted peer bots before they reach core, because cc-connect guardrail feedback uses reply delivery while final agent output uses normal channel sends.
- **FR-005**: Core rate-limit handling MUST NOT emit rate-limit replies for peer-bot-originated messages.
- **FR-006**: Core busy-session queue acknowledgements MUST NOT emit replies for peer-bot-originated messages.
- **FR-007**: Core busy-session overflow and previous-processing paths MUST NOT emit replies for peer-bot-originated messages.
- **FR-008**: Core queued-message drop notifications MUST NOT emit replies for queued peer-bot-originated messages.
- **FR-009**: Core MUST preserve existing human/operator rate-limit, busy queue, overflow, and previous-processing feedback.
- **FR-010**: The implementation MUST remain a Layer 1 transport fix and MUST NOT add coordination policy or broad content-prefix filtering as the primary system-notice filter.

### Key Entities

- **Message author provenance**: a core-level marker on inbound messages, currently needed to distinguish human/operator input from allowlisted peer-bot input.
- **Peer bot message**: an inbound platform message whose author is a bot account explicitly configured in `allow_from_bots`.
- **Bridge/system notice**: cc-connect-generated guardrail feedback such as queued, rate-limited, previous-processing, dropped-queue, or error-notice text.
- **Normal peer output**: a peer bot's final agent answer delivered as a normal Discord channel message.

## Success Criteria

### Measurable Outcomes

- **SC-001**: Focused Discord test proves normal allowlisted peer bot output still dispatches to core with peer-bot provenance.
- **SC-002**: Focused Discord test proves an allowlisted peer bot Discord reply is ignored as a bridge notice.
- **SC-003**: Focused core tests prove peer-bot rate-limit, queue-ack, and overflow/previous-processing paths are silent.
- **SC-004**: Focused core tests prove human/operator rate-limit and busy feedback remains unchanged.
- **SC-005**: After rebuild/restart, PC-7 parent-channel smoke can be retried with zero bridge/system notices entering either peer runtime.

## Assumptions

- Discord is the only platform in scope for this PC-76 blocker.
- Current cc-connect final agent output for Discord is delivered through `Platform.Send`, while guardrail feedback uses reply/drop-notice paths; this slice codifies that distinction for peer-bot isolation.
- Thread-mode repair and live PC-7 smoke execution remain out of scope.
